# SafeFlow-Agent：面试当天前端演示照读稿

这份文档的目标不是介绍代码细节，而是帮助你在面试当天一边操作 Streamlit 页面，一边稳定地把项目讲清楚。

建议用法：

- 面试前 5 分钟先通读一遍
- 演示时按“操作 -> 讲稿 -> 预期画面”的顺序走
- 不需要逐字死背，但可以直接照着念

---

## 一、面试前准备

### 1. 启动命令

```bash
cd /data/hjj2/SafeFlow-Agent
conda activate hjj_rag_env
python -m streamlit run streamlit_app.py --server.address 0.0.0.0 --server.port 8501
```

浏览器打开：

```text
http://<server-ip>:8501
```

### 2. 上台前确认两件事

1. 页面顶部右上角标签里能看到当前推理模式  
   理想情况是：`LLM API 模式`

2. 页面默认是中文  
   如果不是，右上角切回 `简体中文`

### 3. 这次演示想传达的核心

你不是在演示一个聊天机器人，而是在演示一个“多阶段安全决策系统”。

整场演示只要让面试官记住这三点就够了：

1. 系统会先抽事实，不会直接拍结论
2. 证据不足时会先追问，而不是乱判
3. 最终动作可解释、可兜底、可沙箱执行

---

## 二、整场演示总路线

建议顺序：

1. 高风险案例 `ORD-1002`
2. 低风险案例 `ORD-1003`
3. 多模态案例 `ORD-1004`
4. 澄清追问案例 `ORD-1001`

为什么这样排：

- 第一段先展示“多轮追问 + 高风险判断 + 沙箱执行”的完整闭环
- 第二段展示“不会误伤，能做低风险分流”
- 第三段展示“真实多模态附件也能并入 workflow”
- 第四段展示“这个系统不是单轮分类器，而是会先追问”

---

## 三、开场 20 秒

### 你说

我做的不是一个普通聊天机器人，而是一个面向网约车安全投诉场景的多阶段决策 Agent。它会把投诉文本、聊天记录、订单上下文和可选的 OCR、ASR 文本统一处理，然后依次做事实抽取、补充说明追问、SOP 和历史案例检索、风险评估、动作规划、Verifier 复核，最后输出结构化报告，并在沙箱里模拟执行工单和人工审核通知。

### 你此时操作

先不要点按钮，让面试官看到页面整体布局。

### 你可以顺手指一下页面

- 左边是输入和操作区
- 右边是结果总览、证据与策略、流程明细和原始 JSON

---

## 四、案例一：`ORD-1002` 高风险偏航案例

这段是整场最重要的部分。

### 第一步：载入案例

#### 你操作

1. 侧边栏选择 `ORD-1002 | 高风险：偏航与害怕`
2. 点击 `载入当前样例`

#### 你说

我先演示一个偏航场景。这个案例里，乘客投诉司机突然偏航，自己要求下车但司机没有立刻停车，同时聊天记录里能看到乘客质疑路线异常。

#### 你预期会看到

- 左侧订单 ID 自动变成 `ORD-1002`
- 投诉文本和聊天记录自动填好

---

### 第二步：开始评估

#### 你操作

点击左侧 `开始评估`

#### 你说

这一步相当于把案件送入工作流。系统不会直接给一个标签，而是先做输入标准化和事实抽取，再判断当前证据够不够支撑后续决策。

#### 你预期会看到

当前版本里，这个案例第一轮通常会先进入 `等待补充说明`，这是正常的。

页面上会看到：

- 状态：`等待补充说明`
- 人工介入：`需要`
- 证据片段：已经能看到抽取到的投诉和聊天证据
- 待补充信息：`司机解释`
- 系统追问：`司机是否解释过路线变化？你当时是否要求停车或下车？`

#### 你此时重点说

这个结果其实很符合产品设计。系统已经识别出偏航和乘客恐惧这些信号，但因为还缺“司机是否解释路线变化”这个关键事实，所以它没有直接往后做知识检索和最终判定，而是先追问。这正是这个系统和单轮分类器最大的区别之一。

---

### 第三步：展示证据与流程

#### 你操作

切到右侧 `证据与策略` 和 `流程明细`

#### 你说

这里我会优先展示证据，而不是先展示结论。当前系统已经抽到了投诉里的偏航和乘客害怕，也抽到了聊天里的路线质疑。这说明系统已经完成了事实抽取，只是出于保守策略，还没有直接进入最终决策。

#### 你可以顺着讲

流程明细里现在会看到前三步：

1. 输入标准化
2. 事实抽取
3. 澄清门控

这意味着系统在“证据不足时先停下来追问”，而不是盲目继续。

---

### 第四步：提交补充信息

#### 你操作

在左侧 `补充信息` 输入框里填入这句，然后点击 `提交补充信息`

```text
司机没有解释路线变化，我要求停车后他过了大约两分钟才停下，我当时很害怕。
```

#### 你说

我现在补充一个关键事实：司机没有解释路线变化，而且乘客要求停车后司机延迟停车。这个信息补齐之后，系统就可以继续进入知识检索、风险评估和动作规划。

#### 你预期会看到

提交后，这个案例会进入 `可执行`，并生成结构化报告。

当前这版常见结果是：

- 案件类型：`偏航/绕路`
- 风险等级：`高风险`
- 推荐动作：`转人工审核`
- 人工介入：`需要`

#### 你此时重点说

这里我想强调的不是“它判成高风险”本身，而是它为什么能判成高风险。你可以看到，它先补齐关键事实，再做检索和复核，最后才给出可执行的建议。所以整个判断是有证据、有策略、有工作流边界的。

---

### 第五步：展示策略引用与检索结果

#### 你操作

切回右侧 `证据与策略`

#### 你说

这里能看到系统检索出来的策略和案例引用。虽然这个项目里的知识库是合成的，但它体现的是一个真实产品思路：最终决策不能只看投诉文本，还要有 SOP 和历史案例做 grounding。

#### 你补一句更稳

这个 demo 的检索结果是合成数据，所以我更强调它的方法论意义，也就是“决策有依据”，而不是强调某条策略标题本身。

---

### 第六步：执行沙箱动作

#### 你操作

点击左侧 `执行沙箱动作`

#### 你说

现在系统已经有了最终报告，所以我点击执行沙箱动作，看看这套工作流如何把决策映射到自动化动作上。

#### 点击后到底发生什么

这一步不会真的处罚司机，也不会真的给安全团队发消息。它只是在沙箱里模拟两类动作：

1. 创建安全工单
2. 通知人工审核

#### 你预期会看到

右侧 `沙箱执行结果` 会出现两条记录：

- `create_safety_ticket`
- `notify_human_reviewer`

常见返回字段包括：

- 工单号
- 风险等级
- 摘要
- 通知单号
- 原因
- 是否沙箱 = `True`

#### 你此时重点说

这一步体现的是“决策闭环”。也就是说，这个系统不只是能判断，还能把判断转成结构化动作结果。但为了安全和合规，我只做沙箱模拟，不会触发真实业务动作。

---

## 五、案例二：`ORD-1003` 低风险费用纠纷

这一段的目标不是展示复杂流程，而是证明系统不会过度升级。

### 你操作

1. 侧边栏切换到 `ORD-1003 | 低风险：费用纠纷`
2. 点击 `载入当前样例`
3. 点击 `开始评估`

### 你说

第二个案例我想展示的是，这个系统并不是把所有投诉都往高风险上升。这个案例本质上是过路费或退款纠纷，不应该被误判成安全事故。

### 你预期会看到

当前这版常见结果是：

- 状态：`可执行`
- 案件类型：`费用纠纷`
- 风险等级：`低风险`
- 推荐动作：`转客服处理`
- 人工介入：`不需要`

### 你此时重点说

这说明系统除了能召回高风险，也能压住误报，把低风险问题正确分流出去。从产品角度看，这一点很重要，因为真正上线的系统不能什么都打高风险。

---

## 六、案例三：`ORD-1004` 多模态附件案例

这一段的目标是展示“图片/音频附件不是装饰，而是会进入决策链”。

### 你操作

1. 侧边栏切换到 `ORD-1004 | 多模态：音频线索`
2. 点击 `载入当前样例`
3. 点击 `开始评估`

### 你说

这个案例里，乘客主诉比较模糊，但上传了一段司机行程后发来的语音。系统会先在多模态解析阶段把音频转写或 transcript fallback 结果并入案件上下文，再继续走事实抽取、检索和决策，而不是把附件当成独立信息孤立处理。

### 你预期会看到

- 右侧工作流地图里会经过 `多模态解析`
- `证据与策略` 里会出现多模态解析结果
- 最终通常会进入高风险并推荐转人工审核

### 你此时重点说

这一段最想体现的是，我不仅保留了 OCR/ASR 文本入口，还把图片/音频附件接入到了同一条 Agent workflow 里。也就是说，多模态输入不是额外做一个 demo，而是能真实影响后续事实抽取和风险判断。

---

## 七、案例四：`ORD-1001` 证据不足 -> 多轮追问

这一段重点是体现“多轮交互”。

### 第一步：载入澄清追问案例

#### 你操作

1. 侧边栏切换到 `ORD-1001 | 澄清追问：信息不足`
2. 点击 `载入当前样例`
3. 点击 `开始评估`

#### 你说

第三个案例我故意输入一个非常模糊的投诉，看系统会不会乱判。理想行为不是直接输出一个高风险或低风险标签，而是先追问。

#### 你预期会看到

- 状态：`等待补充说明`
- 系统会给出 1 到 2 个追问

当前常见追问是：

- 请你更具体地描述发生了什么，包括对方说了什么、做了什么。
- 这件事发生在行程中、下车后，还是后续联系里？

#### 你此时重点说

这个场景最能体现工作流设计思路。系统没有急着判断，而是先承认“我现在信息不够”，然后继续问。

---

### 第二步：补充具体事实

#### 你操作

在左侧 `补充信息` 输入：

```text
司机在结束后半夜一直给我打电话，还说想单独见面。
```

点击 `提交补充信息`

#### 你预期会看到

当前这版常见结果是：

- 案件类型：`骚扰`
- 风险等级：`高风险`
- 推荐动作：`转人工审核`

#### 你说

一旦补充信息里出现了明确的深夜联系和越界邀约信号，系统就能把案件从“模糊描述”转成“可判断事件”。这说明多轮追问不是为了显得更智能，而是为了提高判断质量。

## 八、收尾 20 秒

### 你说

这个项目我最想体现的能力，不是调了多少 prompt，而是把一个高风险业务里的理解、追问、检索、判断、复核和执行拆成了可落地、可解释、可扩展的工作流。它既能在证据不足时先追问，也能在风险明确时给出结构化动作，并保留人工兜底和沙箱执行边界。

## 九、如果面试官追问“你这个项目里最像 Agent 的地方是什么？”

你可以直接答：

我觉得最像 Agent 的地方有四个。第一，它不是单轮问答，而是状态化、多阶段 workflow。第二，它会在证据不足时主动追问。第三，它会把 RAG 检索结果纳入决策依据，而不是只看投诉文本。第四，它最终不只是给分类结果，还会生成动作建议，并通过 verifier 和沙箱执行把决策闭环起来。

---

## 十、如果面试官追问“执行沙箱动作后到底发生了什么？”

你可以直接答：

点击执行沙箱动作后，前端会调用服务层的 `execute_case`。后端会读取当前 run 的最终报告，根据推荐动作和是否需要人工介入，决定模拟执行哪些工具。高风险案件通常会生成两类结果：一个是安全工单，一个是人工审核通知。它们都会以结构化结果显示在页面上，但不会触发真实业务动作。

---

## 十一、如果面试官问“为什么 `ORD-1002` 第一轮不是直接给最终结论？”

你可以直接答：

因为当前设计故意把“司机是否解释路线变化”当作偏航案件里的关键缺失事实。也就是说，这个案例第一轮已经抽到了证据，但系统仍然选择先追问，再继续做后续检索和决策。这体现的是一种保守、受控的安全产品设计。

---

## 十二、当天最稳的演示习惯

1. 每点击一个按钮之前，先说“这一步是做什么的”
2. 每点击完一个按钮之后，先看状态，再讲原因
3. 优先讲证据、追问和工作流，不要一上来只盯最终标签
4. 少说框架名，多说产品逻辑和安全边界

---

## 十三、一句话提醒自己

不要把自己讲成“我做了个会聊天的大模型页面”，而是讲成：

我做了一个面向高风险场景的多阶段安全决策系统，这个系统会先理解、再追问、再检索、再判断、再复核，最后才进入可控执行。
