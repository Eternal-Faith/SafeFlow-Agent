# SafeFlow-Agent：简历项目描述 + 面试讲稿

## 简历项目描述

### 版本一：偏稳妥，适合直接放简历

基于 `LangGraph 状态工作流 + FastAPI + RAG + Tool Calling` 设计并实现网约车安全决策 Agent，面向乘客投诉场景完成多阶段 workflow 编排。系统对投诉文本、聊天记录、订单上下文及图片/音频附件进行事实抽取、澄清追问、SOP/历史案例检索、风险评分、动作规划与 Verifier 二次校验，输出风险等级、证据引用、处置建议和人工转交决策，并通过沙箱工具模拟安全工单创建、证据快照保留与人工审核通知。

### 版本二：偏技术亮点，适合强调 Agent 能力

从 0 到 1 实现面向网约车安全场景的多阶段 Agent 系统，采用 `LangGraph 多角色工作流 + 规则约束 + LLM 推理 + Verifier 校验` 架构，结合 `RAG`、`工具调用`、`多轮澄清`、`多模态附件解析` 和 `SQLite 持久化`，构建可解释、可降级的安全自动化处置流程；在合成评测集上对比纯规则与单轮推理基线，验证 workflow agent 在风险识别稳定性上的提升。

### 版本三：偏业务导向，适合贴 JD

围绕网约车安全投诉研判场景，构建具备多轮推理、风险排序、流程自动化执行能力的 Agent。通过将复杂处置链路拆解为输入标准化、多模态解析、事实抽取、澄清追问、知识检索、风险决策、动作规划、二次审核和工具执行 9 个阶段，沉淀面向真实业务流程的可复用智能决策模块。

## 简历里可拆成 3 条 bullet

- 设计并实现基于 `LangGraph` 的网约车安全投诉研判 Agent，将输入标准化、多模态解析、事实抽取、澄清追问、RAG 检索、风险评分、动作规划、Verifier 校验和工具执行抽象为多角色状态工作流。
- 构建 `规则约束 + LLM 推理 + RAG grounding` 混合决策机制，引入检索 query 构造、轻量 rerank、人工兜底和工具计划，保证高风险案件可解释、可审计、可降级。

## 面试讲稿

### 1 分钟版本

我做的是一个面向网约车安全投诉场景的决策 Agent，不是普通聊天机器人。用户输入投诉文本、聊天记录和订单上下文之后，系统会先做事实抽取，判断信息是否充分；如果证据不够，会先追问澄清，而不是直接下结论。之后它会检索安全 SOP 和历史案例，结合规则和大模型做风险评分、动作排序，再交给一个 Verifier Agent 做二次审查，最后输出风险等级、证据引用、处置建议，并通过工具调用模拟创建安全工单和通知人工审核。这个项目的重点是把复杂安全流程拆成可解释、可复用、可降级的 workflow。

### 3 分钟版本

这个项目的出发点是，真实的安全投诉场景里，单条投诉文本往往不够，很多信息分散在聊天记录、订单轨迹和补充说明里。如果直接让大模型“一步判断”，很容易出现两个问题：一是证据不足时乱推理，二是高风险案件缺少人工兜底。所以我把整个流程拆成了 8 个阶段。

第一步是输入标准化，把投诉文本、聊天记录、OCR、ASR 和订单上下文统一成一个 case narrative。第二步做事实抽取，识别案件类型、关键信号、证据片段和缺失信息。第三步是澄清门控，如果关键信息不足，就最多追问 2 轮，仍然不足就转人工，而不是让模型脑补。第四步做 RAG，从安全 SOP 和历史案例里检索相关规则和相似案例。第五步在规则约束下做风险评分和优先级排序。第六步生成候选动作，比如转人工、建工单、继续补充信息或者转客服。第七步由 Verifier Agent 校验推荐动作是否真的被证据和 SOP 支撑，如果不安全就强制降级。最后一步生成结构化报告，并做沙箱化的工具执行。

工程上我用的是 `FastAPI + Streamlit + SQLite`，workflow 层基于 `LangGraph` 做多角色状态图编排。考虑到面试项目需要能在本地和服务器上快速跑通，我把模型接入做成 API 可选，同时保留离线 heuristic fallback；对于图片和音频附件，支持真实多模态 API 解析，也支持 OCR/ASR 文本 fallback。这个项目我觉得最大的价值，不是用了多少框架，而是把一个高风险业务流程抽象成了多阶段、可解释、可审计的 Agent workflow。

## 面试时容易被追问的点

### 为什么不用单轮 prompt 直接判断？

因为安全场景里错误代价高。单轮判断的问题是把“理解、推理、执行”耦合在一起，证据不足时容易幻觉，也很难做人工兜底和责任追踪。拆成 workflow 后，每一步都能单独观察和约束。

### 为什么要做 Verifier Agent？

主流程更偏“生成”和“规划”，Verifier 更偏“审查”和“找漏洞”。尤其在高风险业务里，我希望系统默认保守，所以让 verifier 阶段专门检查动作是否真的被证据和 SOP 支撑，这样更符合安全场景的设计思路。

### 为什么还要保留规则，不全交给大模型？

因为有些规则是业务硬约束，比如明显威胁、性骚扰、危险偏航必须人工介入。这类场景不应该交给模型自由裁量。规则负责兜底，模型负责补充语义理解和解释能力，两者结合更稳。

### 为什么做 RAG？

如果只看投诉文本，模型可能会忽略上下文和处置规范。RAG 的作用不是让回答更长，而是让决策有依据，尤其是要能引用具体 SOP 和相似案例，让输出更可解释。

### 为什么工具执行做成沙箱？

因为这是面试项目，不是真实业务系统。如果直接做真实处罚或封禁逻辑，反而会暴露权限、安全和合规问题。沙箱执行更能体现我理解了自动化边界。

### 为什么没有本地部署模型？

第一版我优先考虑开发效率和 demo 可用性，所以采用 API 可选、离线 fallback 默认可用的方式。但在架构上，我已经把 LLM 适配层和 workflow 层解耦，后续如果切本地开源模型，只需要替换推理适配器，不需要重构整体系统。

## 你可以主动强调的亮点

- 我不是只做了一个调用大模型的接口，而是做了完整的决策链路抽象。
- 我考虑了高风险场景下的安全边界，比如人工兜底、规则硬约束和自动化降级。
- 我把 RAG、工具调用、多轮澄清和 verifier 校验放进同一个业务闭环里，而不是分别做 demo。
- 我保留了离线 fallback，这让项目更容易复现，也更适合作为工程化作品展示。
